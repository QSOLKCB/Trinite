# Subsequent Trinite research additions, checked 26 October 2026

Research-only proposals. No experiment, model, runtime or third-party code was executed. Sources below were read directly. Publication dates identify papers or reports, not dates on which Trinite gained a capability. The [v1 roadmap](../ROADMAP-V1.md) already contains dense-first diagnosis, representation/capacity controls, bounded integer inference, RSH conformance and the three-size ladder. These additions extend those milestones rather than replace them. The original [dated assessment](ASSESSMENT-2026-10-22.md) remains supporting context; source claims below are external evidence, not Trinite results.

## Suggested order and integration

### 1. Add component-level resource accounting and artifact-bound provenance now

Extend Milestones 1 and 5: report trainable and total parameters separately; embedding/output-head, transformer, scales and exception tensors; serialized payload, tokenizer and runtime assets; peak resident memory and KV/cache/context memory; prefill and decode latency independently. A small weight file is not the whole deployment footprint. Prefer these measurements before choosing architectural compression.

Pin model/tokenizer/configuration/revision, downloaded artifact digests, trusted source repository and build provenance together. A matching release version or source tag is insufficient evidence about a downloaded artifact. The LiteLLM October 21 incident report states that the official source tag was clean while distributed artifacts were compromised; its October 23 canonical account supersedes early attack-chain assumptions. Neither report establishes exposure in Trinite or Trent's machines. This is a release/admission design lesson, not a proposed incident response or requirement to adopt LiteLLM.

Sources: https://docs.litellm.ai/blog/security-incident-oct-21-2026 and https://docs.litellm.ai/blog/security-incident-oct-21-2026-attack-chain .

Gate: reject mismatched source/artifact/representation commitments; retain the exact accepted inputs; distinguish verified authenticity from mere byte identity. Independent action/evidence reconciliation should include interrupted, resumed and timed-out runs rather than assuming that a final success receipt covers every action.

Monitoring inspiration: METR's October 22 report concerns an historical system on/before July 21, not present-day OpenAI coverage; its evaluators did not verify later patch claims. Apply only the general completeness lesson to Trinite's evidence boundary, not exploit details or an unrelated agent-monitoring subsystem. Source: https://metr.org/blog/2026-10-22-red-teaming-openai-agent-monitoring/ .

### 2. Profile CPU synchronization only after a stable inference reference

The October 20 preprint *Weight Placement Is Not Enough* measures 20–48% synchronization waiting on tested multi-NUMA Xeon ternary decoders. It identifies load imbalance, leader work and partitioning, not only barrier count. Its column-split results are not bit-identical-output guarantees: greedy agreement is limited, activation quantization differs, and the engine has architecture restrictions and omits BitNet-specific operators. It does not establish a Ryzen gain.

Source: https://arxiv.org/html/2610.28620v1 .

Proposal: within Milestone 5, compare one-thread and bounded worker-count runs at identical workloads; separate useful compute, wait/imbalance, memory traffic and serialization. Report topology/affinity and warm/cold conditions. Retain the exact-output reference lane; numerical/quality-changing kernels need a separate declared tolerance/backend identity. No default multi-node architecture or automatic thread oversubscription.

### 3. Progressive ternary QAT as a controlled alternative, not a replacement

TernScope (October 21 preprint) is a 248,300-parameter medical-segmentation CNN, not an LLM. Its staged recipe quantizes a fused graph, with all 25 convolutions eventually ternary and activations at eight bits. Floating master weights/scales and wider bias/scaling/accumulation remain. Hardware area and power claims are synthesis/estimated evidence, not measured CPU/GPU or whole-device gains. The paper's training recipes differ, so its tables are not proof that schedule alone caused every gain.

Source: https://arxiv.org/html/2610.29617v1 ; released project link https://github.com/ReaganWu/TernScope .

Proposal: extend Milestone 4 with direct-versus-progressive QAT only after a useful dense checkpoint, matching initialization, data, exposure, optimizer and validation selection. Explicitly version which layers transition and when, calibration, scales, rounding and saturation. Choose final checkpoints only after the full target representation is active. Report quality, code occupancy and complete resource footprint separately; do not claim integer training or acceleration from fake quantization. Review code/weights licences before reuse.

### 4. SQuAT: optional E8 quantizer/gradient ablation

SQuAT (October 22 preprint) separates vector direction and gain and uses separate straight-through estimators. Its evidence compares quantizers/initialization at billion-parameter and multi-billion-token scales. It is lattice vector quantization, not the existing ternary scalar lane. The paper identifies efficient E8S dequantization as unresolved; broader architecture generalization is unproven. Code is promised upon acceptance, not established available here.

Source: https://arxiv.org/html/2610.31412v1 .

Proposal: retain an optional, separately named bounded lane comparing joint versus factored gradient estimators under identical codebook, initialization, data and exposure. Start with deterministic codebook/nearest-neighbor/tie/scale fixtures. Record codebook construction and all scale/metadata bits, not just nominal weight bits. Do not mix this with RSH, new curricula or capacity increases. Gate on task quality plus real deployment cost; geometry conformance or reconstruction error is not evidence of reasoning improvement.

### 5. Frozen binary embeddings only if vocabulary cost becomes material

*Embeddings Are Overpriced?* (October 15 preprint, surfaced October 22) derives binary codes from pretrained Gemma embeddings. Its single-seed comparison includes worse overall validation loss for frozen tables, while selected downstream scores improve/tie. Ternary-arm differences also include schedule and prior changes. Its CPU speed result uses one laptop and different codebases, and excludes prefill. The released table inherits Gemma terms and the project is non-commercial research; these are not scratch-trained, licence-neutral features.

Source: https://arxiv.org/html/2610.22428v1 ; artifact index https://huggingface.co/QLNI/embeddings-are-overpriced .

Proposal: first measure whether Trinite's admitted small vocabulary has a meaningful embedding/head cost. If justified, compare learned embeddings, fixed random codes, and licensed pretrained-derived codes as separate arms. Match architecture, exposure and output scoring; disclose inherited pretrained knowledge, tokenizer and frozen bytes. Include loss, rare-token behavior, exact task quality and head compute. Keep this outside the native capacity experiment to avoid conflating external information with added parameters.

### 6. Defer MLIPS until sparse long-context indexing exists and dominates

MLIPS (October 20 preprint) shares a broad candidate pool while retaining per-layer selection. Reported serving gains are for DeepSeek-V4-Flash on four GB300 GPUs; single-run accuracy changes include regressions, and more reuse can worsen quality. It is not a general exact-cache optimization or evidence for tiny dense models. Its exploratory Top-G deployment benefits remain open.

Source: https://arxiv.org/html/2610.27438v1 .

Proposal: record as deferred OPT/QSOL-MESH crossover, conditional on a measured full-prefix candidate-search bottleneck. A future trial must retain independent consumer scoring, measure candidate coverage and end-task quality, and specify invalidation/refresh semantics. Do not add sparse-attention infrastructure to Trinite merely to apply this paper.

## 7. shrek_GPT: small artifacts need a full deployment ledger

The [source-pinned assessment](SHREK-GPT-ASSESSMENT.md) reviews Amine Harrabi's
January 2026 experiment as newly supplied research, not a new October release.
Its retained notebook reports 124.44M pretrained GPT-2 parameters in a 63.66 MiB
mixed-precision GGUF model buffer, but also 144 MiB KV and 99.66 MiB compute
buffers. Those are logged allocations, not measured whole-process peak memory.
The notebook's final export reads the original fine-tuned directory rather than
the separately saved sparsified directory; it does not establish one serial
NF4 → sparse → GGUF pipeline. It contains no held-out quality evaluation or
LoRA adapter construction, despite the repository description.

Transfer the lessons, not implementation with unestablished reuse rights or the movie-text corpus:
independently bind every transformation's input/output identities, prove the
export derives from the intended checkpoint, separate model-file bytes from
runtime/KV/scratch memory, and use bounded context plus held-out quality tests.
Keep pruning, quantization, representation and training interventions separate.
No repository licence or released weights/data was found at the reviewed pin.
Nothing from this project is admitted into native Trinite training.

The owner's related compute/KV request is specified separately in
[the compute and cache harness proposal](../COMPUTE-KV-HARNESS-PROPOSAL.md).
An uncached measurement harness is feasible without a new model, but a real
native KV cache requires an explicitly versioned incremental inference path.
Current full-prefix execution is not described as cached merely because an
external model engine exposes cache metrics.

## Scope exclusions

Unrelated quantum-hardware and retro-hardware digest stories do not become core
Trinite upgrades. Exact-math references may later justify separate donor
conformance, not a learned-reasoning claim. No third-party corpus, code, weights
or terms are adopted by listing a source here.

## Overall gates

All above are prospective, not adopted performance guarantees or permission to run experiments. Preserve historical protocols, caps and immutable v0.4.0 evidence. Select one diagnosis-driven intervention at a time, predeclare quality/resource acceptance, retain negative outcomes, and require independent conformance before optimized execution. The first implementation priority remains the canonical native diagnostic workflow, not an architecture shopping list.
